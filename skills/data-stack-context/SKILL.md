# Data Stack Context

I help you create and maintain a foundational context document for your data stack so every other analytics engineering skill can work without asking redundant setup questions.

## Check for Existing Context

First, check if `.claude/data-stack-context.md` already exists:

```
Does `.claude/data-stack-context.md` exist in this project?
```

- **If yes**: Read the file and present a summary. Ask: "Would you like to update any sections, or is this still accurate?"
- **If no**: Proceed to draft or build the context document.

## Two Paths to Build Context

### Path A: Auto-Draft from Codebase (Recommended)

Scan the project for these files and extract configuration automatically:

| File | What to extract |
|---|---|
| `dbt_project.yml` | Project name, model paths, materializations, adapter hints |
| `profiles.yml` | Warehouse type, target names (dev/prod), schema patterns |
| `packages.yml` | dbt packages in use (Elementary, dbt_utils, etc.) |
| `requirements.txt` / `pyproject.toml` | Python dependencies, orchestrator hints |
| `.env` / `.env.example` | Environment variable names (not values) |
| `Dockerfile` / `docker-compose.yml` | Infrastructure hints |
| `*.github/workflows/*.yml` | CI/CD tool and trigger patterns |
| `airflow/` or `dags/` | Orchestrator = Airflow |
| `dagster/` or `dagster.yaml` | Orchestrator = Dagster |

After scanning, produce a draft and say: "I've auto-drafted your context from the codebase. Please review and correct anything that's wrong or missing."

### Path B: Conversational Build

Ask these questions in batches (do not ask one at a time):

**Batch 1 - Core Infrastructure:**
1. Which data warehouse? (Snowflake / BigQuery / Databricks / Redshift / DuckDB / Other)
2. Which transformation tool? (dbt Core / dbt Cloud / SQLMesh / Other) — if dbt, which version?
3. Which orchestrator? (Airflow / Dagster / Prefect / dbt Cloud jobs / GitHub Actions / None)

**Batch 2 - Surrounding Tools:**
4. Which BI layer? (Looker / Metabase / Lightdash / Tableau / PowerBI / None)
5. Data observability? (Elementary / Monte Carlo / Soda / Great Expectations / None)
6. Data catalog? (OpenMetadata / Atlan / dbt docs only / None)
7. Ingestion tool? (Fivetran / Airbyte / Stitch / Custom / Mixed)

**Batch 3 - Team and Scale:**
8. Team size and maturity? (Solo / Small 2-5 / Mid 6-15 / Large 15+)
9. Data volume? (GB-scale / TB-scale / PB-scale, plus rough row counts for your largest tables)
10. Cost constraints? (Tight / Moderate / Unconstrained)

**Batch 4 - Business Context:**
11. Compliance requirements? (GDPR / CCPA / HIPAA / SOC2 / None)
12. Key data sources? (e.g., Salesforce, Stripe, Shopify, internal Postgres, etc.)
13. Environments? (dev/staging/prod, which CI/CD tool?)
14. North star metrics? (The 3-5 metrics the business cares most about)

## Output Format

Save the completed context to `.claude/data-stack-context.md` using this exact template:

```markdown
# Data Stack Context
<!-- Generated by data-stack-context skill. Update as your stack evolves. -->

## Warehouse
- **Platform**: Snowflake  <!-- Snowflake / BigQuery / Databricks / Redshift / DuckDB -->
- **Edition/Version**: Enterprise
- **Default database**: analytics
- **Schema conventions**: <env>_<domain> (e.g., prod_core, dev_staging)

## Transformation
- **Tool**: dbt Core
- **Version**: 1.8.x
- **Adapter**: dbt-snowflake
- **Project name**: my_project

## Orchestration
- **Tool**: Dagster
- **Pattern**: dbt assets wrapped in Dagster software-defined assets
- **Schedule cadence**: hourly for staging, nightly for marts

## BI Layer
- **Tool**: Metabase
- **Connection**: connects directly to prod warehouse
- **Key dashboards**: Revenue overview, Churn analysis, Growth metrics

## Observability
- **Tool**: Elementary
- **Coverage**: all mart and core models have anomaly detection
- **Alerting**: Slack #data-alerts channel

## Data Catalog
- **Tool**: dbt docs (hosted via dbt Cloud)
- **Update frequency**: on every prod deploy

## Ingestion
- **Tool**: Fivetran
- **Key connectors**: Salesforce, Stripe, Shopify, Google Ads
- **Custom pipelines**: internal Postgres via Airbyte

## Environments
- **dev**: developer-local, schema = dev_<username>
- **staging**: CI runs on PR open, schema = ci_<pr_number>
- **prod**: merges to main trigger deploy, schema = prod_*
- **CI/CD**: GitHub Actions

## Team
- **Size**: Small (3 analytics engineers, 2 analysts)
- **Maturity**: Intermediate — dbt in production, some testing gaps
- **Code review**: required, 1 approval

## Data Volume
- **Scale**: TB-scale
- **Largest tables**: events (~2B rows), orders (~50M rows), sessions (~500M rows)
- **Warehouse spend**: ~$8k/month

## Cost Constraints
- **Level**: Moderate
- **Notes**: Optimize for query cost on large scans; avoid full table scans in dev

## Compliance
- **Regulations**: GDPR, CCPA
- **PII handling**: masked in dev/staging via dbt macros, audit log required
- **Data retention**: 2 years for raw, 7 years for financial

## Key Sources
- **CRM**: Salesforce (accounts, contacts, opportunities)
- **Payments**: Stripe (charges, subscriptions, invoices)
- **Ecommerce**: Shopify (orders, products, customers)
- **Product**: internal Postgres (events, sessions, feature flags)
- **Marketing**: Google Ads, Facebook Ads

## North Star Metrics
1. **Monthly Recurring Revenue (MRR)** — primary growth metric
2. **Net Revenue Retention (NRR)** — expansion vs churn signal
3. **Activation Rate** — % of signups completing key onboarding step
4. **Customer Acquisition Cost (CAC)** — blended across paid channels
5. **Daily Active Users (DAU)** — engagement proxy
```

## Maintenance Guidelines

- **Update triggers**: new tool added to stack, team size change, compliance requirement added, major dbt upgrade
- **Who updates**: any analytics engineer, reviewed by team lead
- **Format**: keep the same section headers so other skills can parse reliably
- **Do not store**: passwords, API keys, or connection strings — only tool names and patterns

## Usage by Other Skills

Every other analytics engineering skill will read this file at the start with:

```
Read .claude/data-stack-context.md to understand the current data stack before proceeding.
```

If the file does not exist, those skills will invoke this skill first.
